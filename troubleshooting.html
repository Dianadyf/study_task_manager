Project Plan - Three-Week Sprint

The application was developed following a clear, structured three-week sprint. The table below outlines each stage of the sprint, what was planned for that week, and the deliverables produced.

Stage Week Activities Deliverables
Planning Week 1 (early) Defined the purpose of the application, identified user needs (students managing assignments, revision and deadlines), listed the required pages and features. Feature list, page structure (Home, Task Manager, Troubleshooting Blog, Ethics & Privacy).
Analysis Week 1 Analyzed what data a task needs (title, course, due date, description, priority), decided on browser localStorage for persistence and a simple login gate. Data requirements list, validation rules, storage design.
Design Week 1 - 2 Sketched the layout of each page, chose a consistent colour scheme and typography, designed the task table and the create/update form. Shared stylesheet, page wireframes, navigation design.
Implementation Week 2 Built the HTML pages, CSS styling and JavaScript logic: login, create, update, delete with confirmation, ordered task table and live date/time footer. Working web application (all four pages functional).
Testing & Maintenance Week 3 Tested every feature (valid and invalid input, editing, deleting, login errors), fixed bugs found during testing, documented errors in this blog, refactored code. Tested and polished application, this troubleshooting blog.

Bugs Encountered During Development

The following errors were encountered while implementing the create, update, delete, validation and interface behaviour of the application. For each error, this page records the date and time, a screenshot, the code snippet that caused the problem, and a detailed troubleshooting explanation with the date/time it was solved, a screenshot of the working application and the corrected code.

Error 1: Tasks were displayed in random order instead of ordered by due date

When the problem occurred

Date & time: 20 May 2026, 10:35 AM - discovered while testing the "View all study tasks" feature after adding five tasks with mixed due dates.

Screenshot of the problem

[INSERT SCREENSHOT: task table showing tasks listed in insertion order, e.g. a task due 30/05 appearing above a task due 22/05]

Code snippet that caused the problem

function renderTasks() {
  var tbody = document.getElementById("task-table-body");
  var tasks = loadTasks();  // BUG: tasks are used directly in storage order

  tbody.innerHTML = tasks.map(function (t) {
    return "<tr><td>" + t.title + "</td>...</tr>";
  }).join("");
}

When the problem was solved

Date & time: 20 May 2026, 12:10 PM.

Screenshot of the working application

[INSERT SCREENSHOT: task table now sorted from the earliest due date to the latest, with the "Due soon" and "Overdue" status labels visible]

Corrected code snippet

function renderTasks() {
  var tbody = document.getElementById("task-table-body");
  // FIX: copy the array and sort it by due date before rendering
  var tasks = loadTasks().slice().sort(function (a, b) {
    return a.dueDate.localeCompare(b.dueDate); // YYYY-MM-DD sorts chronologically
  });

  tbody.innerHTML = tasks.map(function (t) {
    return "<tr><td>" + t.title + "</td>...</tr>";
  }).join("");
}

Explanation

  • Possible cause: localStorage returns tasks in the order they were created, not in the order of any field inside them. The requirement says tasks must be displayed in an ordered format, so rendering the raw array did not satisfy it.
  • How it was solved: the array is copied with slice() (so the stored data is never mutated) and sorted with localeCompare(). Because due dates are stored in ISO format YYYY-MM-DD, comparing the strings sorts them chronologically without converting to Date objects.
  • Resources / references: MDN Web Docs - Array.prototype.sort() and String.prototype.localeCompare(); lecture notes on storing structured data with localStorage and JSON.

Error 2: Invalid dates were accepted by the create-task form

When the problem occurred

Date & time: 22 May 2026, 2:48 PM - discovered during data-validation testing when a due date typed as 2026-02-31 (a date that does not exist) was accepted, and the task appeared with a wrong due date.

Screenshot of the problem

[INSERT SCREENSHOT: form accepting 2026-02-31 as the due date and the task being saved without any error message]

Code snippet that caused the problem

function isValidDate(value) {
  // BUG: JavaScript rolls overflow dates forward instead of rejecting them
  var d = new Date(value);
  return !isNaN(d.getTime());   // 2026-02-31 becomes 2026-03-03, so this returns true
}

When the problem was solved

Date & time: 22 May 2026, 4:05 PM.

Screenshot of the working application

[INSERT SCREENSHOT: red validation message "Invalid date: please enter a real calendar date (YYYY-MM-DD)." shown under the Due Date field, task not saved]

Corrected code snippet

function isValidDate(value) {
  // FIX 1: the value must match the exact YYYY-MM-DD pattern
  if (!/^\d{4}-\d{2}-\d{2}$/.test(value)) return false;
  var d = new Date(value + "T00:00:00");
  if (isNaN(d.getTime())) return false;
  // FIX 2: round-trip check - the date must convert back to the same string,
  // so impossible dates like 2026-02-31 are rejected
  return value === d.toISOString().slice(0, 10);
}

Explanation

  • Possible cause: the JavaScript Date constructor automatically "rolls over" impossible dates (February 31 becomes March 3), so checking only for NaN lets invalid dates through. This broke the requirement that invalid dates must be rejected.
  • How it was solved: two checks were added - a regular expression that enforces the YYYY-MM-DD shape, and a round-trip comparison between the input string and toISOString() output, which only matches for real calendar dates. Past dates are also rejected using a separate daysUntil() check.
  • Resources / references: MDN Web Docs - Date.prototype.toISOString() and regular expressions in JavaScript; W3Schools HTML date input validation guide.
